* Goal and scope

Deliver the ZetaX =z= namespace, native Zig/Forge engineering boundary, and a
pure Zig logging component compatible with current zpp configuration and the
zust pattern subset. Baseline: exact Zig 0.17.0, Linux x86_64, no libc or third-party
logging backend. Overall status: accepted awaiting versioned delivery.
Actual versioned delivery remains unset until an authorized version commit.

Non-goals: other foundational components, full spdlog pattern grammar, runtime
backend plugins, multiprocess file sharing, hot configuration/timezone reload,
leap seconds, other-platform runtime acceptance or a production-maturity claim.

* Architecture and ownership

Dependency direction is =z facade -> log runtime -> config/time/format/output=.
Types form the shared value contract; infrastructure modules do not depend on
the facade or application policy. General and independent facades reuse the
same module object. Compile-time level selection and type-directed JSON field
loading use Zig facilities; no extra forwarding or dynamic sink registry exists.

The application owns allocator, Io, environment and producer shutdown. The
runtime owns immutable configuration/timezone snapshots, compiled patterns,
file buffers, queue and worker/flusher. One successful singleton init is allowed;
failures publish nothing. Shutdown closes admission, waits for references,
drains and joins before releasing memory. A small static admission gate and
static futex reference count keep lifetime coordination independent of runtime
allocation. A static atomic mask on an independent cache line is derived from
the shared routing function and updated by control operations under the gate.
It only rejects calls early; it neither publishes Runtime nor replaces lifetime
references. Admitted calls recheck routing. Level updates serialize with close
and cannot republish enabled bits after shutdown. State transitions are
fresh -> initializing -> ready -> closing ->
closed; failed init returns to fresh. Formatter reentrant shutdown/flush is unsupported.

Hot-path boundaries: filtered calls do not format or allocate; short payloads
use stack storage and inline queue slots; output render/file buffers are reused.
Async queues discard incoming data and flush requests when full. Explicit flush
is best-effort admission, not a completion barrier; shutdown drains and joins. Long payloads allocate explicitly.
A single async worker establishes accepted order; independent output failures
are observable without suppressing healthy destinations.

Forge owns the shared Zig adapter, toolchain validation and safe profile cleanup.
zzg owns native build steps, modules, tests, samples and public configuration.
Existing zpp/zust sources are read-only compatibility references. Native tests,
fixed clocks/records, deterministic timezone fixtures and isolated process
scenarios provide seams without a public plugin system.

* Overall acceptance and remaining boundaries

Overall acceptance requires the integrated shared suite and example, not just
individual Stage checklists. Version 0.1.0 metadata is prepared, not a released
commit. zeta_forge's adapter acceptance does not imply a Forge version bump or
release. No commit/push, full workspace build, long soak, sanitizer or other
platform acceptance is implied. Subsequent optimization must preserve these
contracts and compare repeatable benchmarks before increasing complexity.

* Calendar formatting optimization (2026-10-22)

This optimizes the existing logging path without renumbering Stages 1.1-1.4.
Owner: zzg, with no new cross-repository prerequisite. Compiled patterns record
calendar requirements; actual output routes trigger lazy conversion, sharing
one most-recent-UTC-second calendar cache per Runtime. Fractions remain per
record. Timezone snapshots, async record timestamps, output bytes and public
APIs are preserved. Formatted-time caching, specialized numeric output and
arbitrary fragment caching are outside this delivery.

Acceptance covers deterministic conversion counts, DST/backward/out-of-order
timestamps, synchronous producers and queued async records, existing
Debug/ReleaseFast integration suites, and seven paired ReleaseFast comparisons
using the same benchmark source. See the [[file:verification.org][validation record]] for results and
status; actual delivery version remains unset.
